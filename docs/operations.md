# 공개 서버 운영

독립 Linux 서버 한 대, Docker Compose, 서비스 도메인의 DNS A/AAAA, 80·443 포트가 필요합니다. 계정·세션·예약이 같은 영속 디스크를 사용하는 **단일 노드 구조**입니다. 서버리스 함수나 정적 호스팅에 그대로 올리면 예약이 작동하지 않습니다.

```sh
python3 deploy/configure.py alerts.example.org   # 실제 도메인으로 교체
docker compose up -d --build
docker compose ps --all
curl --fail https://alerts.example.org/healthz
```

`migrate`는 종료 코드 0이 정상입니다. `web`, `worker`, `proxy`는 계속 실행됩니다. 프록시가 이미 있는 장비에서는 두 번째 프록시를 띄우지 마세요. 기존 프록시 전용 네트워크에 web만 연결하고 새 도메인만 web:8000으로 라우팅합니다. 기존 사이트 설정은 유지하고 Caddy validate 후 reload하세요. 외부에서 Gunicorn·데이터 볼륨에 직접 접근할 수 없어야 합니다. 신뢰한 프록시는 X-Forwarded-Proto와 X-Real-IP를 실제 연결 값으로 덮어써야 합니다.

**점검 순서:** healthz → 테스트 계정 가입 → 두 번째 계정에서 첫 계정 방이 보이지 않는지 확인 → 합성 프로필/방 저장 → 워커 실행 확인 → 이용자 본인의 허가된 테스트 키·채널로 미리보기와 1건 발송. 운영자 키를 전체 이용자에게 공유하지 않습니다.

- 서명·암호화 키는 초기 한 번 생성하고 재배포 때 유지합니다. `.env` 유실 시 토큰 복호화가 불가능합니다. 키 파일과 볼륨 백업은 분리하고 복구 연습은 별도 환경에서 하세요.
- 데이터 볼륨 삭제나 `down -v`는 일반 업데이트 절차가 아닙니다. 안정된 태그/커밋과 백업을 확보하고 이전 이미지로 되돌릴 경로를 확인하세요. DB 스키마 변경이 있으면 별도 마이그레이션 및 롤백 검토가 필요합니다.
- 실행 시각을 놓친 방은 재기동 때 한 번만 처리합니다. API 장애를 0건으로 기록하지 않으며 실패한 실행을 자동 반복하지 않습니다. 시간 초과는 외부 발송 여부가 불명확하므로 재실행 전에 대상 채널을 확인하세요.
- 한 노드에서 회원별 실행을 잠급니다. 동시 사용량이 늘면 CPU·메모리·디스크, 예약 지연, 발송 오류와 제공자 과금부터 관측하세요. DB를 네트워크 파일시스템으로 공유하거나 웹 컨테이너만 여러 노드로 늘리는 것은 지원하지 않습니다.
- 기본 가입 정원은 100명(환경변수 JOBEVENT_MAX_ACCOUNTS), 계정당 12개 방입니다. 수동 실행·가져오기에는 시간당 제한이 있습니다. 이는 비공개 초대제가 아니라 공개 베타의 용량 제한입니다. 이용자 수 확장 전 계정 복구·백업 보존 기간·문의 대응·운영 정책도 마련하세요.
