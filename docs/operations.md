# 공개 서버 운영

독립 Linux 서버 한 대, Docker Compose, 서비스 도메인의 DNS A/AAAA, 80·443 포트가 필요합니다. 계정·세션·예약이 같은 영속 디스크를 사용하는 **단일 노드 구조**입니다. 서버리스 함수나 정적 호스팅에 그대로 올리면 예약이 작동하지 않습니다.

```sh
python3 deploy/configure.py alerts.example.org   # 실제 도메인으로 교체
docker compose up -d --build
docker compose ps --all
curl --fail https://alerts.example.org/healthz
```

`migrate`는 종료 코드 0이 정상입니다. `web`, `worker`, `proxy`는 계속 실행됩니다. 프록시가 이미 있는 장비에서는 두 번째 프록시를 띄우지 마세요. 기존 프록시 전용 네트워크에 web만 연결하고 새 도메인만 web:8000으로 라우팅합니다. 기존 사이트 설정은 유지하고 Caddy validate 후 reload하세요. 외부에서 Gunicorn·데이터 볼륨에 직접 접근할 수 없어야 합니다. 신뢰한 프록시는 X-Forwarded-Proto와 X-Real-IP를 실제 연결 값으로 덮어써야 합니다.

**점검 순서:** healthz → 테스트 계정 가입 → 두 번째 계정에서 첫 계정 방이 보이지 않는지 확인 → 합성 프로필/방 저장 → 워커 실행 확인 → 이용자 본인의 허가된 테스트 키·채널로 미리보기와 1건 발송. 운영자 키를 전체 이용자에게 공유하지 않습니다.

- 서명·암호화 키는 초기 한 번 생성하고 재배포 때 유지합니다. `.env` 유실 시 토큰 복호화가 불가능합니다. 키 파일과 볼륨 백업은 분리하고 복구 연습은 별도 환경에서 하세요.
- 데이터 볼륨 삭제나 `down -v`는 일반 업데이트 절차가 아닙니다. 안정된 태그/커밋과 백업을 확보하고 이전 이미지로 되돌릴 경로를 확인하세요. DB 스키마 변경이 있으면 별도 마이그레이션 및 롤백 검토가 필요합니다.
- 실행 시각을 놓친 방은 재기동 때 한 번만 처리합니다. API 장애를 0건으로 기록하지 않으며 실패한 실행을 자동 반복하지 않습니다. 시간 초과는 외부 발송 여부가 불명확하므로 재실행 전에 대상 채널을 확인하세요.
- 한 노드에서 회원별 실행을 잠급니다. 동시 사용량이 늘면 CPU·메모리·디스크, 예약 지연, 발송 오류와 제공자 과금부터 관측하세요. DB를 네트워크 파일시스템으로 공유하거나 웹 컨테이너만 여러 노드로 늘리는 것은 지원하지 않습니다.
- 기본 가입 정원은 100명(환경변수 JOBEVENT_MAX_ACCOUNTS), 하루 신규 가입은 30명(JOBEVENT_DAILY_SIGNUPS), 계정당 12개 방입니다. 수동 실행·가져오기에는 시간당 제한이 있습니다. 이는 비공개 초대제가 아니라 공개 베타의 용량 제한입니다. 이용자 수 확장 전 계정 복구·백업 보존 기간·문의 대응·운영 정책도 마련하세요.

## 자동 배포 (공유 서버)

앱 화면·API·워커는 하나의 이미지입니다. 서버는 약 3분 주기로 공개 저장소 main을 확인하고 해당 SHA의 **push CI 성공**이 확인될 때만 새 이미지를 빌드합니다. PR·포크 코드를 운영 서버에서 실행하지 않으며 GitHub에 SSH 키/운영 API 키를 저장하지 않습니다. 웹훅 수신 포트를 추가하지 않습니다.

- 신뢰 경계: 배포 스크립트와 systemd 설정은 운영자가 검토 후 별도 설치합니다. 매 배포 시 Git에서 내려받은 스크립트를 root로 재설치하지 않습니다. 기존 호스트의 Compose·키·HTTPS 프록시·데이터 볼륨은 보존합니다.
- 구성: `deploy/cd/pull-release.sh` → `/usr/local/libexec/jobevent-cd`, `deploy/cd/jobevent-cd.{service,timer}` → systemd. `/etc/jobevent-cd.conf`에 기존 스택 경로(JOBEVENT_STACK_DIR), 배포 기록 파일(JOBEVENT_REVISION_FILE), 공개 HTTPS 상태 주소(JOBEVENT_HEALTH_URL)를 설정합니다. 구성에는 사용자 키를 넣지 않습니다.
- 후보 이미지의 운영 설정과 미적용 마이그레이션 여부를 점검합니다. **미적용 DB 변경은 배포하지 않습니다.** 백업·호환성·복구 절차를 사람이 검토한 뒤 별도로 적용합니다. 그 외 호스트의 Compose/시스템 설정 변경 역시 별도 검토 대상입니다.
- 전환 후 외부 healthz의 SHA·worker의 이미지와 실행 상태를 두 번 확인합니다. 실패하면 이전 이미지로 되돌리고 해당 SHA는 재시도하지 않습니다. 이 롤백은 볼륨이나 DB를 되돌리지 않습니다.
- 점검: `systemctl status jobevent-cd.timer`, `journalctl -u jobevent-cd.service`, 공개 `/healthz`, GitHub Actions의 Production delivery. 장애 시 먼저 타이머를 멈추고 이전 이미지, 두 서비스 상태, 데이터 무결성을 확인합니다. 원인을 해결한 뒤에만 실패 표식을 해제하고 재시작합니다.
- 매주 ARM64 이미지의 실제 설치 패키지를 다시 검사합니다. 이 감사는 Python 패키지의 알려진 취약점 검사이며 OS·프록시·하루 사이의 신규 공개 취약점까지 전부 보증하지 않습니다.

Vercel 프로젝트는 같은 저장소의 `deploy/entry`만 배포하는 Git 연동입니다. 실제 앱/API/워커는 OCI에서 실행되고, Vercel에는 사용자 키·운영 SSH 키를 저장하지 않습니다.
