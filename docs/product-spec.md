# Jobevent 공개 베타 제품 명세

## 대상과 핵심 결과

운영·개발자는 두 명이고, 이용자는 초대나 개발 권한 없이 가입하는 구직자·학생·활동 지원자다. 성공의 단위는 추천 글자 수나 설치 수가 아니라 **한 이용자가 확인할 가치가 있는 신규 공고를 원하는 방과 시간에 받는 것**이다. 자동 지원, 이력서 대필, 채용 자격 보증, 고객 정보 수집은 하지 않는다.

## 결정 기록

| 결정 | Jobevent에서 이 선택이 맞는 이유 | 기각한 대안 / 전환 조건 |
|---|---|---|
| 반응형 웹 + 홈 화면 설치(PWA) | 입력은 가입·초기 프로필·간헐적 방 편집에 집중되고 결과는 이미 쓰는 Discord/Slack에서 소비한다. 설치 없이 가입하고 PC·폰에서 같은 설정을 본다. | 모바일 단독 스케줄러는 백그라운드 실행 시점을 통제할 수 없다. 네이티브 앱은 앱에서만 해결 가능한 작업(공고 저장·공유 확장·직접 푸시)이 반복 확인된 후 검토한다. |
| OCI 상주 워커, 가입 링크만 Vercel | 이미 운영하는 서버에서 브라우저/휴대폰과 무관하게 예약을 돌릴 수 있다. Vercel은 가입 경로만 리디렉션해 자격 증명을 처리하지 않는다. | 모든 요청을 서버리스로 옮겨도 예약·데이터 저장은 따로 필요하다. 단일 장애점은 수용하되 복구 경로와 백업을 먼저 검증한다. |
| Django 세션 + 회원별 SQLite, 파일 잠금 | 개발자 두 명이 인증·CSRF·비밀번호 해시를 직접 구현하지 않는다. 한 노드의 웹/워커가 같은 볼륨을 사용하므로 별도 DB·브로커 없이 방별 중복 확인이 가능하다. | 수평 확장이 필요하면 파일 잠금을 네트워크 디스크에 옮기지 않는다. PostgreSQL 트랜잭션, 작업 임대와 전송 이력을 먼저 설계한다. |
| 제공 회사 선택 + 모델 자동 배정 | 사용자에게 모델 ID를 입력시키지 않는다. 선택한 회사에만 해당 키를 보내고, 검색과 개인 자료 기반 선별을 분리한다. | 다른 회사로 자동 폴백하지 않는다. 회사 변경 시 새 키가 필요하다. 메타데이터 없는 생성 링크는 보내지 않는다. |
| 출처를 선택하는 방 | 특정 회사는 Greenhouse/Lever 공개 원본이 검색보다 싸고 범위가 명확하다. 동아리·대회는 공통 공식 API가 확인되지 않아 출처 링크가 있는 검색을 쓴다. | 전체 웹을 무차별 크롤링하지 않는다. 새 소스는 공개 가능 범위·마감 의미·오류/빈 목록 구별·원문 링크를 확인해야 채택한다. |
| 사용자 키·원문 보관 최소화 | 서버에서 예약을 실행하려면 키에 접근해야 한다. 암호화는 DB 단독 유출을 완화하지만 운영자로부터 데이터를 숨기지는 못한다. | 본문 없이 회원별 오류·건수 위주로 기록한다. 모든 프롬프트/이력서를 분석 로그에 쌓지 않는다. |
| 매일/요일별 현지 시각, 방별 소량 발송 | 지원 기회는 분 단위 시세가 아니다. 사용자가 검색비와 알림 피로도를 통제할 수 있게 한 번에 1~8건만 전달한다. | 초단위 cron, 불확실한 실패 시 무제한 재전송은 제외한다. 예약 시각은 시작 목표이지 외부 서비스까지의 정시 도착 보장이 아니다. |

## 베타 사용 흐름과 합격 조건

1. 비회원은 키·프로필을 볼 수 없다. 가입 뒤 키 없이 화면과 설정을 탐색할 수 있다. 한 계정의 방 ID를 알아도 다른 계정에서는 조회·수정·발송할 수 없다.
2. PDF·텍스트·지원되는 공개 링크를 가져와 내용을 확인하고 편집한 뒤 저장한다. 프로필은 공개 검색어로 전송하지 않는다. 키·웹훅을 대시보드에 복원하지 않는다.
3. 템플릿은 방 초깃값일 뿐이다. 예컨대 월~금 09:00 채용 알림과 토요일 14:00 공모전 알림은 목적지·말투·실행 시각·최대 건수가 독립적이어야 한다.
4. 미리보기는 발송·소진 이력이 없다. 실제 전송은 사전 인용/수집된 URL로 제한하고 알려진 지난 마감은 제외한다. 중복은 같은 방 기준으로 판단한다. 검색·추천·전송 실패와 신규 결과 없음은 구분한다.
5. 브라우저를 닫거나 로그아웃해도 활성 예약은 계속된다. 재시작 후 밀린 실행을 모두 재생해 과금하지 않는다. 계정 탈퇴 뒤에는 예약·키·회원별 저장소가 남지 않는다.
6. 휴대폰에서 계정 생성·방 설정이 가능해야 한다. 별도 네이티브 앱에 서버 키를 내려주지 않는다. 오프라인에서는 안내만 표시하고 프로필·추천을 캐시하지 않는다.

## 한도와 다음 투자 판단

100계정, 계정당 12방은 **측정된 수용량이 아니라 작은 공유 서버를 보호하는 베타 상한**이다. 100명이 12개 방을 모두 같은 시각에 예약하면 1,200회가 몰릴 수 있다. 예를 들어 방 하나당 5초라고 가정해도 단일 워커로 100분이다. 이 값은 가정이며 실제 처리량이 아니다. 정원을 늘리기 전에 예약 집중도, 모델 응답 대기, 실행 지연을 합성 부하로 측정한다.

| 다음 결정 | 앞으로 수집할 근거 | 행동 |
|---|---|---|
| 검색 개선 vs. 소스 추가 | 채용·동아리·대회별로 표본을 나눠 원문이 열리는지, 실제 접수 중인지, 사용자가 지원 가능한지 사람이 독립 판정. URL이 없는 결과는 실패로 센다. | 한 분류에서 반복 오탐이면 모델 교체 전에 해당 소스·필터부터 수정한다. 아직 정확도 수치는 발표하지 않는다. |
| 병렬 워커/DB 전환 | 같은 시각에 활성 방 10·50·100개를 예약한 합성 시험에서 예약→시작 지연 p95와 중복·누락을 확인한다. 최초 운영 검토선은 10분이며 고객에게 제시한 SLA가 아니다. | 지연의 원인이 검색 대기면 제한된 작업 동시성부터, 잠금/다중 노드라면 DB·큐 전환을 검토한다. |
| 모바일 앱 투자 | 모바일 가입자가 키 등록→첫 미리보기를 완료하지 못하는 단계와 이유를 실제 사용자에게 확인한다. 첫 실기기 검증은 iOS Safari·Android Chrome 각 1대에서 파일 업로드/설치/재로그인. | 키 발급·웹훅 설정이 문제면 앱을 새로 만드는 대신 온보딩을 고친다. 직접 푸시 수요가 확인되면 푸시 어댑터부터 검증한다. |
| 회원 확대 | 계정 복구·운영 문의, DB·키 백업 복원, 비용과 오류 고지, 삭제 동작을 점검한다. | 확인 없이 사용자 한도부터 풀지 않는다. 자료 수집이나 분석 SDK는 이용자 고지 없이 추가하지 않는다. |

설치 가능한 웹과 네이티브 앱은 다르다. 현재 배포는 PWA와 Discord/Slack 전송이며 앱스토어 출시, 자체 푸시, 실기기 호환 인증을 의미하지 않는다. 플랫폼 선택의 공식 근거와 유사 사례는 [설계 조사](design.md)를 참고한다.
