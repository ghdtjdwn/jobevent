# Jobevent 제품 명세

## 대상과 핵심 결과

이용자는 GitHub에서 직접 설치해 쓰는 개발 직군 대학생·개발자다. 유지보수자는 두 명이고 서버를 운영하지 않는다. 성공의 단위는 설치 수나 추천 글자 수가 아니라 **한 이용자가 확인할 가치가 있는 신규 공고를 원하는 방과 시간에 받는 것**이다. 다루는 기회는 채용·인턴·동아리·공모전·해커톤·교육·장학·오픈소스와 직접 정의다. 차별점은 셀프 실행, 이용자 키(BYOK), 목적별 알림방, 팀 채널 전달의 조합이다. 자동 지원, 이력서 대필, 채용 자격 보증, 이용자 정보 수집은 하지 않는다. 소개에 '취업추천·취업지원' 표현을 쓰지 않는다.

## 결정 기록

2026-11-26 두 유지보수자 논의(#19~#33)에서 공개 호스팅 서비스를 접고 로컬 설치형 오픈소스로 전환했다. 각 결정의 근거와 기각한 선택지는 해당 논의 이슈의 `논의 결과`에 있다.

| 결정 | 이유 | 기각한 대안 / 다시 논의할 조건 |
|---|---|---|
| 이용자 PC에서 실행하는 로컬 앱(127.0.0.1 웹 화면) + Discord·Slack 전달 (#21) | 서버 운영·개인정보·법적 책임을 지지 않는다. 설정은 가끔, 결과 확인은 이미 쓰는 메신저에서 한다. | 공개 웹(PWA), 모바일·데스크톱 앱, 웹 푸시, 메신저 봇만. 예약은 PC와 프로세스가 켜져 있을 때만 실행된다. |
| 회원가입·로그인·연령 확인 없음 (#24, #25) | 단일 사용자 앱이라 계정과 복구 대상이 없다. 같은 기기만 쓰도록 Host·Origin을 검사한다. 제공 회사 약관(예: Gemini 만 18세 이상) 준수는 이용자 책임으로 README에 적는다. | 아이디·비밀번호, Discord 로그인, passkey, 초대제. 백업은 `~/.jobevent` 폴더 복사로 안내한다. |
| BYOK, 키·웹훅은 OS 자격 증명 저장소 (#22, #23) | 키가 기기를 떠나지 않으면서 예약 실행이 가능하다. 대상이 개발 직군이라 웹훅 붙여넣기 안내로 충분하다. | 서버 암호화 보관, 브라우저 보관, OpenRouter OAuth, 운영자 키 체험, Discord·Slack OAuth, Telegram·이메일·카카오. 요청이 생기면 새 이슈. |
| 제공 회사 선택 + 모델 자동 배정 | 모델 ID를 입력시키지 않는다. 선택한 회사에만 해당 키를 보내고, 공개 조건 검색과 개인 자료 기반 선별을 분리한다. | 다른 회사로 자동 폴백하지 않는다. 회사를 바꾸면 새 키가 필요하다. |
| 출처: 제공 회사 웹 검색 + Greenhouse·Lever 공개 보드 (#27) | 인용된 원문 링크만 후보로 쓴다. 회사 보드는 검색보다 싸고 범위가 명확하다. | 사이트별 수집기(데이터베이스권 위험), 국내 공식 API(사업자 키라 배포 불가), Dev-Event(라이선스가 금지). |
| 자료 원문은 로컬 SQLite, 공고 알림에 `[AI 추천]` 표시 (#26) | 이용자가 자기 키로 자기가 고른 회사에 직접 보내므로 유지보수자는 처리자가 아니다. 채널 멤버는 AI 추천임을 알아야 한다. | 요약만 저장, 처리방침·국외 이전 동의 게시. 유지보수자가 데이터를 받는 기능을 만들면 다시 논의한다. |
| 직업정보제공사업 신고·질의 안 함 (#20) | 유지보수자는 공고를 모으거나 제공하는 서버 없이 MIT 소프트웨어를 배포한다. 법률 자문 결과가 아니다. | 공고를 모아 다른 사람에게 전달하는 호스팅을 다시 하면 새 논의 이슈에서 정한다. |
| 표준 라이브러리 HTTP 서버, SQLite, keyring, filelock, 빌드 없는 HTML/JS (#31) | 단일 이용자·단일 기기라 수평 확장과 회원 격리가 필요 없다. 의존성이 적을수록 설치 실패와 보안 갱신 부담이 준다. | Django, PostgreSQL·작업 큐, React. |
| MIT, GitHub 태그 설치, 비용·수익화 없음 (#29, #32) | 이용자가 저장소를 보고 설치하는 경로와 같고 PyPI 계정 관리가 필요 없다. AI 사용료는 이용자 키로 부담한다. | PyPI 배포, 정식 도메인, 후원·유료 플랜·스폰서 공고. |
| 추천 품질은 변경 시 수동 판정 (#28) | 사용 데이터를 밖으로 보내지 않는다. 프롬프트·모델·출처를 바꾸는 PR과 릴리스에서 분류마다 10건을 판정한다. | 메시지별 피드백 링크(추적 서버 필요), 매주 정기 판정. |
| 매일/요일별 현지 시각, 방별 소량 발송 | 지원 기회는 분 단위 시세가 아니다. 검색비와 알림 피로를 이용자가 통제하도록 한 번에 1~8건만 보낸다. | 초 단위 예약, 불확실한 실패의 무제한 재전송. 예약 시각은 시작 목표이지 정시 도착 보장이 아니다. |

## 사용 흐름과 합격 조건

1. `uv tool install`로 설치하고 `jobevent`를 실행하면 브라우저에서 바로 알림방 화면이 열린다. 키 없이도 화면과 설정을 탐색하고 자료를 저장할 수 있다. 다른 출처의 웹페이지는 설정을 읽거나 바꿀 수 없다.
2. PDF·텍스트·지원되는 공개 링크를 가져와 내용을 확인·편집한 뒤 저장한다. 자료는 공개 검색어로 전송하지 않는다. 키·웹훅을 화면에 돌려주지 않는다.
3. 템플릿은 방 초깃값일 뿐이다. 예컨대 월~금 09:00 채용 알림과 토요일 14:00 공모전 알림은 목적지·말투·실행 시각·최대 건수가 독립적이어야 한다.
4. 미리보기는 발송·소진 이력이 없다. 실제 전송은 인용·수집된 URL로 제한하고 알려진 지난 마감은 제외한다. 중복은 같은 방 기준으로 판단한다. 검색·추천·전송 실패와 신규 결과 없음은 구분한다.
5. 프로세스가 실행 중이면 브라우저를 닫아도 예약이 계속된다. 꺼져 있던 동안 놓친 예약은 다음 실행 때 방마다 한 번만 처리하고 밀린 회차를 모두 재생해 과금하지 않는다. 방을 삭제하면 그 방의 웹훅과 기록이 남지 않는다.

## 다음 투자 판단

| 다음 결정 | 앞으로 수집할 근거 | 행동 |
|---|---|---|
| 검색 개선 vs. 소스 추가 | 변경 PR·릴리스마다 분류별 10건의 원문 열림·접수 중·지원 가능 판정. URL이 없는 결과는 실패로 센다. | 한 분류에서 반복 오탐이면 모델 교체 전에 해당 소스·필터부터 고친다. 수치가 쌓이기 전에는 정확도를 발표하지 않는다. |
| 설치 경험 | 첫 이용자들이 설치, 키 발급, 웹훅 연결 중 어디서 멈추는지 이슈로 확인한다. | 패키징을 새로 만들기 전에 README와 화면 안내부터 고친다. |
| 새 채널·로그인·OAuth | 실제 이용자의 반복 요청. | 공용 앱 등록이나 운영자 비밀값이 필요한 기능은 새 논의 이슈에서 정한다. |

플랫폼 선택의 공식 근거와 유사 사례는 [설계 조사](design.md)를 참고한다. 이 조사는 호스팅 서비스 시절의 기록이며 현재 결정은 위 표가 우선한다.
